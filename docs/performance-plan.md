### 等價改寫

1. `channel_difference`／`changed_fraction`：uint8 `max−min` 取三通道最大值、整數計數除以像素數；與 `np.max(np.abs(int16 差))`、`np.mean(mask)` 逐位元相同（測試 `test_difference_matches_int16_original`），267 µs → 34 µs。相同影格以 `np.array_equal` 短路。
2. `analysis_pixels`：執行緒區域快取的 `VideoReformatter` 轉 `rgb0`，`Image.frombuffer("RGBX", ..., line_size)` 零拷貝建圖後 BILINEAR 縮放、丟棄第四通道；與舊路徑逐像素相同（含 150 px 寬、line size 有填充的 fixture）。
3. `frames_identical`：以 uint64 視圖比較解碼影格全部平面緩衝區；相同即沿用前一幀像素與 `(0.0, 0.0)` 差分。比較填充位元組只會造成多餘轉圖，不會誤判相同。
4. `iter_prepared_frames`：手動有界佇列（deque）取代 `Executor.map`，worker 任務串接前一幀的 future，在 worker 內以同一個 `difference()` 算出相鄰幀分數與面積；`StableDetector.feed(reference, pixels, precomputed=None)` 接受預算值。FIFO 提交順序保證前一個任務永遠先開始，不會死鎖。
5. 預設 `workers=8, buffer_size=16, decoder_threads=0`；短測與全片量測 4／8／12 workers 差異在 10% 內。

## 實作順序

### 1. 可重現基準與一致性參照

先建立 `scripts/benchmark_analysis.py`，沿用目前依賴，以 `perf_counter` 記錄總分析耗時、解碼／轉圖／判定統計、處理影格數、吞吐量、記憶體峰值、worker／buffer 數、Git 提交、影片 SHA-256 與套件版本。平行階段統計不能直接相加當成總時間，牆鐘時間才是驗收依據。

在 [tests/test_analysis.py](../tests/test_analysis.py) 鄰近加入舊流程參照或測試 helper，保存未優化的前處理和偵測結果作 oracle；勿只用已被修改的同一函式同時產生預期與實際值。先跑短片，最後只需一次完整 160 px 舊版分析建立同寬度參照，且仍須持續回報與可取消。

預設參數以外，覆蓋高敏感度、長穩定時間、零／極小面積門檻、慢轉場、持續動態及片尾；避免優化只對靜止畫面有效。

### 2. 分析專用的少拷貝前處理

在 [analysis.py](../src/video_frame_cutter/analysis.py) 新增小型分析影像轉換函式，移除可避免的 RGB／Pillow 轉換與拷貝，保留相同縮放尺寸計算、BILINEAR、通道次序及 dtype。暫不修改匯出與精確預覽共用的 `display_image`。

先針對旋轉 0、SAR 為空或 1 的情況啟用經验证路徑；旋轉或非方形像素保持舊處理，直到專門測試證明一致。加入有格線／彩色邊緣的影片，檢查 RGB 像素、尺寸與方向，避免只用純色 fixture 得到過度樂觀結論。

單執行緒結果一致與短測通過後，才進入下一階段；若像素不一致，修正轉換或保留原前處理，不直接改成較寬鬆的測試。

### 3. 有界、有序的平行流程

保留外層 Qt `Job`，在分析工作內使用 `ThreadPoolExecutor` 平行處理「不同影格的轉圖與縮放」，單一 decoder 按展示順序產生影格。每個任務獨占該影格，不跨執行緒共用 container 或可變的色彩轉換器。

使用 Python 3.14 的 `Executor.map(..., buffersize=...)` 或等價有限佇列，讓結果始終以原影格／PTS 順序交給同一個 `StableDetector`。**不將穩定偵測器任意切片平行執行**，以免破壞跨片段的 baseline、anchor、min_interval 和逾時狀態。

先測 2 個 workers、buffer 4；再比較 3／4 workers、buffer 6／8，並量測 decoder `thread_count` 與 `AUTO` 的組合，避免 FFmpeg 和 Python 執行緒過量競爭。選足夠達標的最小配置，保留單 worker fallback，不直接開滿 16 個 workers。

取消須停止提交新任務、取消尚未開始的 future，讓執行中的短任務檢查取消旗標，再等待 executor 結束後才釋放 decoder。worker 例外向上傳遞，絕不可用較少影格的部分結果報告成功。所有 GUI 更新仍在主執行緒。

### 4. 只在仍未達標時追加微優化

重新量測占比，再決定是否減少 `astype`、差分陣列與重複基準計算。優先重用完全相同輸入的中間結果；保持 SSIM 算法、浮點精度、閾值比較和每幀曲線不變，特別測門檻附近值。

若上述同結果方案仍無法穩定低於 300 秒，回報實測瓶頸，另行討論原生縮放、灰階或其他算法。這些不在目前授權範圍，不會默默替换。多程序、GPU、整片預載入與快取不是首選，避免 IPC、記憶體和部署成本抵銷收益。

### 5. GUI 整合與驗收報告

延伸 [原片驗收測試](../tests/test_real_video.py) 及 [驗收執行器](../scripts/verify_real_video.py)，獨立記錄 `analysis_elapsed_seconds`、影格數、worker 配置、最大 GUI 心跳間隔與原片一致性。總程序逾時不等於分析 300 秒門檻，二者分開判定。

保留每 5 秒進度、耗時與結果日誌；顯示的是已依序完成判定的影格数，不是提交進佇列的數量。100% 必須代表所有幀已驗證且偵測器 finish 已完成。切换影片、取消、關閉視窗與過期結果丟棄都要回歸測試。

## 驗收條件

1. 同寬度舊版／新版完整分析的影格 PTS、每幀分析像素與 SSIM 曲線一致；標記 PTS、change_seconds、score、review、included 及順序一致。UUID 是新建識別，不要求相同。若想放寬任何數值容忍度，須先確認，不擅改演算法。
2. 160 px 同原片、同參數、無結果快取，在 GUI 工作路徑連續 3 次分析，各次都低於 300 秒，報告最慢一次及中位數。每次重新開啟解碼流程；記錄首次／OS 檔案快取較熱的後續結果，不宣稱清除了 OS 快取。未達標先停止重複長測，返回瓶頸診斷。
3. 保留全部 60,741 幀，沒有任務丟失、重複、亂序或假 100%。480 px 另跑一次結果與效能回歸，無須強行達到 300 秒。
4. 原片仍能逐幀、播放、編輯標記／裁切及匯出；批次結果套用仍保留手動修改。原片 SHA-256 不變，匯出圖像不受前處理優化影響。
5. 取消後沒有殘留 worker、未提交分析結果不覆蓋現有標記；正常本機檔案處理的取消回應目標 2 秒內、GUI 心跳最大間隔目標 1 秒內。另記錄慢磁碟／解碼錯誤的限制。
6. 佇列和 worker 數有上限，前處理不因片長而累積完整影格；量測記憶體相對舊版的增量，目標不超過 256 MiB。既有索引與曲線仍按片長使用記憶體，不能誤報整個程式為常數記憶體。
7. 全部 pytest、ruff、依賴檢查通過；更新 README 的實測時間與適用硬體，提交小步驟到本分支，驗收通過才提出合併，不直接修改或推送 `main`。
